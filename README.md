# SysPulse

macOS 菜单栏实时系统监控：**网速、内存、CPU、GPU** 一目了然，点击展开详细面板。

- 原生 Swift + SwiftUI 实现，无第三方依赖，无网络请求，不收集任何数据
- 常驻菜单栏，不占用程序坞（`LSUIElement`）
- 空闲开销约 **0.02% CPU / 47 MB 内存**（刷新周期 1 秒；打开过面板后弹窗窗口的
  约 38MB 由 AppKit 持有，不会归还）。开了「流光」背景后约 **0.13% CPU**
  （15fps 持续重画，默认关闭）。完整实测数据见「开发备注」的开销一节。

> **接手这个项目请先读完本文件。** 源码、构建脚本、以及所有踩过的坑都在这里；
> 改动流程是「改 `Sources/` → `./build.sh`（自动编译 + 安装到 /Applications + 重启）
> → 用 `screencapture` 截图 / `Tools/Clicker` 合成点击验证」。
> 详见文末「开发备注」和「开发流程」。

## 下拉面板

点击菜单栏图标展开：

- **CPU**：总占用、用户 / 系统占比、核心数、最近 60 秒曲线
- **GPU**：利用率（驱动 `Device Utilization %`，与活动监视器同源）、核心数、曲线；
  副标题里的「GPU 内存」是**当前被 GPU 占用的统一内存**（Apple Silicon 没有独立显存，
  该字段在 Intel 独显机器上才是真正的 VRAM）
- **内存**：占用比例、已用 / 总量、交换分区、曲线
- **网络**：下行 / 上行速度、双线曲线、本次开机累计流量

底部工具栏：刷新频率（0.5 / 1 / 2 / 5 秒）、排版、开机自启、退出；
指标开关（网速 / CPU / 内存 / GPU）单独做成一块卡片（在网络卡片下方）：第一行是标题，第二行是四个横向排列的小开关，可以随手连点。
开关的排版与上方卡片共用同一套网格：徽章 20pt、「图标 + 标题」间距 7pt，所以四张卡片的
标题在同一条竖线上；标题行与开关行之间留 9pt（7 + 2）拉开层次。勾位用固定宽度占位，
勾出现 / 消失时标签不左右移动；四个开关等宽铺满卡片（`maxWidth: .infinity` 均分），
右侧不留缺口，和卡片里的进度条顶到同一条边缘。
三个菜单里选中的项都会在文字前显示一个**绿色勾**——系统自带的勾是单色模板图
（`Toggle` 和 `Label(_:systemImage:)` 都改不了颜色），所以这里用富文本前缀自己画。
未选中项用 5 个空格占同样的宽度（实测「✓  」18.34pt vs 5 空格 17.90pt），
这样所有标题在同一列对齐，未选中项也不会留下任何痕迹。
（`.clear` 和近零透明度在菜单里会被忽略，仍会显示一个淡勾，只能用空格占位。）

## 构建与安装

```bash
cd SysPulse
./build.sh                 # 编译 + 安装到 /Applications/SysPulse.app（唯一副本）并启动
./build.sh --local         # 只打包到本目录 dist/，不安装
./build.sh --no-launch     # 安装但不自动启动
```

`build.sh` 使用 `swiftc` 直接编译，产出 `arm64` + `x86_64` 通用二进制并做临时签名
（ad-hoc），不需要 Xcode 工程。它会先退出正在运行的实例，并在安装后清掉本目录里的
旧副本——**机器上只保留 `/Applications/SysPulse.app` 一份**。

如果 `--local` 打包过，`dist/` 里会多出一份；App 启动时也会优先转交给
`/Applications` 那份并自行退出，所以不会出现两个菜单栏图标。

> **注意 `build.sh` 的安装判定用的是 `[ -w /Applications ]`**（当前用户是否可写），
> 而不是"实际能不能创建文件"。如果 `/Applications` 是 `root:admin drwxrwxr-x`、
> 当前用户属于 `admin` 组且目录**属于别人**，`[ -w ]` 会返回假，脚本会误判为不可写、
> 静默改成只打包到 `dist/`，并且**已经先把正在运行的实例退出了**——结果是监控停了、
> `/Applications` 里还是旧版。这种情况下要手工装回去：
>
> ```bash
> rm -rf /Applications/SysPulse.app
> cp -R dist/SysPulse.app /Applications/SysPulse.app
> codesign --force --deep --sign - /Applications/SysPulse.app
> open /Applications/SysPulse.app
> ```
>
> （App 会主动把控制权转交给 `/Applications` 那份，所以直接 `open dist/SysPulse.app`
> 验证不到新代码。）

开机自启可以在面板的「启动」菜单里开关，也可以走命令行：

```bash
/Applications/SysPulse.app/Contents/MacOS/SysPulse --enable-login-item
/Applications/SysPulse.app/Contents/MacOS/SysPulse --disable-login-item
/Applications/SysPulse.app/Contents/MacOS/SysPulse --login-item-status
```

卸载：先退出，再 `rm -rf /Applications/SysPulse.app`；偏好设置残留在
`~/Library/Preferences/com.local.syspulse.plist`。

App 会**优先使用「应用程序」里的那一份**：同时只允许一个实例（文件锁兜底），
如果从别处启动而 `/Applications/SysPulse.app` 存在，它会自动转交给后者并退出，
避免菜单栏出现两个图标、偏好与开机自启互相打架。

## 命令行自检

```bash

```

会打印一次全部指标，用于确认数据源在本机是否可用：

```
CPU         : 22.0%  (用户 14.8% / 系统 7.2%, 10 核)
GPU         : 83.0%  显存 1.1 G
内存        : 73.1%  已用 13 G / 17 G  交换 2.5 G
网络下行    : 2.6 M/s
网络上行    : 19 K/s
```

## 数据来源

| 指标 | 采集方式 |
| --- | --- |
| CPU | `host_processor_info(PROCESSOR_CPU_LOAD_INFO)`，对每个核心的 tick 做差分 |
| GPU | IOKit `IOAccelerator` 服务的 `PerformanceStatistics.Device Utilization %` |
| 内存 | `host_statistics64(HOST_VM_INFO64)`：活跃 + 联动 + 压缩页；交换分区来自 `sysctl vm.swapusage` |
| 网络 | `sysctl(NET_RT_IFLIST2)` 读取 64 位网卡计数器并差分 |
| 其他 | 运行时长取 `systemUptime`，进程数取 `sysctl KERN_PROC_ALL` |

几点说明：

- 网速只累加物理接口（`en*`），排除 `lo0` 与 `utun*`，避免 VPN 隧道流量被重复计算。
- 内存口径与「活动监视器」接近（活跃 + 联动 + 压缩），因此比例通常高于「内存压力」的直观感受。
- GPU 利用率来自 Apple GPU 驱动计数器，与「活动监视器」的 GPU 一栏同源。

## 网速是怎么算出来的

每 1 秒（可配置）读一次内核的网卡字节计数器，用两次采样之差除以真实间隔：

```
下行速度 = (本次 ifi_ibytes − 上次 ifi_ibytes) / 实际经过秒数
```

几个要点：

- **单位是十进制的 MB/s**：`M` = 1000²，所以菜单栏的 `↓2.8M` 表示 2.8 MB/s ≈ 22 Mbps。
  如果你习惯看 Mbps，乘以 8 即可。
- **统计的是整块网卡的全部流量**：所有 App、所有系统服务（iCloud、mDNS、推送、
  App Store、系统更新）都算在内，不区分进程。
- 只统计物理接口 `en*`，不含 `lo0`（本机回环）与 `utun*`（VPN 隧道），
  否则同一份流量会被算两次。

### 为什么"什么都没干"也有一两 MB/s？

先确认是不是真有后台流量。macOS 自带 `nettop` 可以按进程看：

```bash
nettop -l 1 -x -n -P -J bytes_in,bytes_out | sort -k2 -nr | head
```

本机实测（20 秒窗口）：

| 来源 | 下行 |
| --- | --- |
| `netstat -ib` en0 计数差 | 3.37 MB/s |
| `nettop`：抖音 单个进程 | 3.18 MB/s |
| SysPulse 读数 | 2.8 – 3.4 MB/s |

三者一致——也就是说读数没问题，是**抖音在后台下载**（短视频预加载/自动播放），
它一个进程就占了全部下行流量的 94%。

常见的"空闲流量"来源：短视频类 App 的预加载、iCloud 照片与云盘同步、
App Store / 系统更新、浏览器后台标签页、`mDNSResponder` 等系统服务。

### 一个已修复的内核计数器坑

`netstat -ib` 显示 en0 累计接收 70 GB 时，通过 `sysctl NET_RT_IFLIST2` 读到的
`ifi_ibytes` 却只有 1.4 GB —— 因为**这个字段实际会按 2³² 回绕**（70 GB mod 4 GiB
正好等于 1.4 GB；`ifi_ipackets`、`ifi_obytes` 则是正确的 64 位）。用包数可以佐证：
5600 万个接收包不可能是 1.4 GB（平均 26 字节/包，低于以太网 64 字节最小帧）。

因此：

- **速率**：差分做了 32 位回绕补偿，任何时刻都准确（早期的写法在回绕瞬间会掉到 0）；
- **累计流量**：内核给不出可信的开机以来总量，只能由程序自己逐次累加，
  面板里显示为「本次运行接收 / 发送」。


## 关于刘海与菜单栏空间（重要）

带刘海的 Mac 上，菜单栏被切成两块可用区域。实测本机（1710pt 宽）：

```
辅助区域左: 0 – 762.5pt    刘海禁区: 762.5 – 947.5pt    辅助区域右: 947.5 – 1710pt
```

**只要状态栏项的窗口跨进刘海禁区，系统就完全不会绘制它**——进程还在、`isVisible` 仍是
`true`、`window.frame` 也正常，但屏幕上什么都没有。实测边界：窗口左边缘要落在
**约 985pt 之后**才会被画出来（比安全区起点还要再留约 40pt 余量）。

而这台机器的右侧状态区已经被 14 个图标占满，只剩约 **86pt**，两行带标签的版本窗口宽
约 89pt —— 差 3pt，于是整个图标被吞掉。多一个 App 图标就会重演。

### 三档排版

| 档位 | 样子 | 宽度 |
| --- | --- | --- |
| 单行（全部指标） | `↓2.9M  CPU 30  GPU 60  MEM 62` | ~215pt |
| 两行 | `↓2.9M  MEM 62` / `CPU 30  GPU 60` | ~110pt |
| 两行（极简） | `↓2.9M` / `30 60 62` | ~80pt |

两行档把指标拆成 **网速 + 内存 / CPU + GPU**：两行宽度接近，比「三个指标挤一行」
窄约 40pt（实测 137pt → 95pt），更适合菜单栏紧张的情况。
两行共用第一列宽度（按 `CPU 100` 的最宽槽位算），所以第二列的 `MEM` 和 `GPU` 上下对齐。

- 指标用**全称标签** `CPU / GPU / MEM`，顺序与下拉面板的卡片一致（CPU → GPU → 内存）。
- 菜单栏只显示**下行**速度；上行速度在鼠标悬停提示和下拉面板里。

**宽度是固定的，不会随数值变化跳动。** 每一小段都按"最宽可能值"预留槽位——
速度永远占 `↓888M` 的宽度、百分比永远占 `CPU 100` 的宽度，实际数字画在槽位内。
所以 `↓0B` 变成 `↓9.9M`、`CPU 9` 变成 `CPU 100` 时，整条读数纹丝不动。

> ✅ **2026-09-16 晚更正：这里原先记的「已知缺陷」不成立，是量宽工具在骗人。**
> 曾经写过「`full`（单行）和 `minimal`（极简）里网速段的 `slot` 被 `columnSlots` 覆盖丢掉，
> 于是按实际文字排版，宽度会 159 ↔ 213pt 地变」。核对源码与实测后**两点都不对**：
> - `MenuBarImage.buildRows` 的 `full` / `minimal` 分支**根本不传 `columnSlots`**，
>   网速段一直带着 `↓888M` 槽位；
> - 用当前源码重测（`build/WidthAudit`）：四项指标齐全时，三档在 **9 种速度 × 3 种百分比**
>   共 27 组取值下宽度漂移 **0.0pt**（full 213.0 / compact 105.0 / minimal 72.0，全部恒定）。
>
> 旧结论来自 `Tools/LayoutProbe` 的 `narrowestSnapshot()`：它**没设 `gpuUsage`**，
> 而 `MetricsSnapshot.gpuUsage` 是 `Double?`，于是"全零"那一组的 **GPU 段整个消失**，
> 宽度自然少了 54pt(full) / 23pt(minimal)。**是探针在骗人，不是排版有 bug。**
> 该函数已补上 `gpuUsage`，文件头也写清了"命令行工具链缺 SwiftUIMacros 插件、
> 要配 `Tools/LayoutProbe/Stub.swift` 才编得过"的配方。

### 空间不够时怎么办

- **选了「自动适应」**：**优先用单行**；每次数据刷新都读一遍状态栏项的真实横坐标，挤不下就降一级
  （单行 → 两行 → 极简），空间回来了再升回去（升档要求更宽那档确实装得下，避免来回横跳）。
  **降档看最近 2 拍**、**升档看最近 5 拍**（保守，理由见下文 bug 6）。
  ⚠️ **判定的"一拍"就是「刷新」周期**（0.5/1/2/5 秒），所以把刷新调慢会让适应一起变迟钝：
  降档约 2 拍、升档约 1 拍 —— 2 秒刷新时约 4 秒 / 2 秒，1 秒刷新时约 2 秒 / 1 秒，5 秒刷新时约 10 秒 / 5 秒。
  想让它更快就把「刷新」调到 1 秒；细节见 `DEVLOG-换档适应延迟-2026-09-16.md` 第 6 节。
- **明确选了某个档位（单行／两行）**：**保持该档位不变**，不会偷偷换成窄的。
  空间真的不够时，交给 macOS 自己的菜单栏收纳——系统会把放不下的项折叠起来并显示
  一个折叠箭头，点开后会在刘海左侧展示。

> **升降档的阈值必须拉开距离。** 曾经的写法是「余量 < 0 就降级、余量 > 30 就升级」，
> 结果降级后条目变窄、左边缘右移、余量立刻变大，于是又升回宽档，宽档又放不下——
> 每秒左右反复横跳，宽档那一秒还会被刘海整条吞掉。
> 现在升档必须确认**更宽那一档的宽度装得进当前余量**。
>
> ⚠️ **2026-09-15 补记（三个 bug 叠在一起，别重蹈覆辙）**
>
> **bug 1：流光把档位判定频率抬到了 15Hz。** 流光为了让画面动起来每帧都会调
> `updateStatusItem` 重画图片；如果让它顺带执行升降档判定，就会以 15Hz 反复决策——
> **测量值还没稳定就被下一次决策推翻**，档位在 `full(213) ↔ compact(105) ↔ minimal(72)`
> 之间每秒一轮无限横跳，图标位置左右跳 190pt，菜单栏看起来像在"转"。
> 修法：`updateStatusItem(with:allowLayoutChange:)`，**流光帧一律传 `false`**，
> 只有数据真的刷新（1~2 秒一次）才允许重算档位。
>
> **bug 2（这才是"明明有空间却停在两行档"的元凶）：升档判据里 `gain` 的变量顺序写反了。**
> 正确是 `gain = iconWidth(更宽档) − iconWidth(当前档)`；写成
> `iconWidth(当前档) − iconWidth(更宽档)` 会得到**负数**，于是 `guard gain > 0`
> 永远不成立、升档分支**永远进不去**。表现就是：自动档有余量也永远停在两行档
> （只有手动切到单行档才看得到单行）。
> **这个 bug 从最初就存在，和流光、和抖动都无关**——一度被误判成"阈值太保守"。
>
> **bug 4（2026-09-16，"明明有空间却不升档"的真正答案）：升档判据看错了参考位置。**
> 旧写法用的是"**当前档**的余量"：`slack > gain + buffer`。但当前档（两行）本来就窄、
> 余量当然够，于是被误判成"够升单行"。正确要看的是**升档之后的左边缘**——
> 升档会多占 `gain`，左边缘会相应左移：
> ```
> effectiveMinX - gain >= safeArea.minX + 40 + buffer
> ```
> 实测反例：两行档 `minX=1072`（余量 84.5，看着很够），但升到单行要多占 108，
> 左边缘落到 **964**，而"画得出来"要求 ≥ **988**（安全区起点 948 + 40），
> 差 24pt —— 所以**单行那 213pt 是真的放不下**，不是阈值留太多。
> 旧写法会误升，然后单行整条被刘海吞掉，看起来就像"被系统折叠了"。
>
> 顺带说明那个 **40pt** 的来历：它不是"我想留的余量"，而是**实测的不可绘制边界**
> （窗口左边缘要落在安全区起点之后约 40pt 才画得出来，见上文刘海那节）。
> 另外还要注意系统在拥挤时会把状态项**挪到极左的折叠区**（实测 minX 在 956 与 513
> 之间跳），所以余量取"最近 5 次采样的最大 minX"，避免被这种瞬时位置骗到而误降档。
>
> **bug 3：降档时"一路降到放得下"，会跳过没测量过的中间档。**
> 降级判断依赖"下一档的图标宽度"，而没渲染过的档位宽度是 `0`（未知）；
> 一路降就会跳过中间档，导致那一档**永远没被测量**、之后再也升不回去
> （实测：冷启动后一路卡在极简档、`densityWidths[1]` 始终是 0）。
> 修法：**一次只降一级**，让中间档有机会渲染一次被测量；升档则要求两级都已测量
> （未测量的宽度是 0，`gain` 自然不为正，就不会升）。
>
> 另外升降档后加 2 秒冷却（`densityCooldown`），避开切换过程中的过渡测量值。
> **最终实测**：`target` 恒为 1、`slack`/`minX` 在 40 秒内零变化；
> 连拍 6 帧的图标文字位置逐帧完全相同。
>
> 另外，单行档早期用的是 `CPU 30%  RAM 74%  GPU 79%` 全称，实测 **261pt**，
> 而菜单栏右侧通常只剩 200pt 上下，于是会出现"能降级但永远升不回单行"的现象。
> 改成与两行档相同的短标签后降到约 160pt，才算真正可用。
>
> **bug 5（2026-09-16，面板箭头"换档时先反向跳一下"）：系统拿"旧 x + 新宽度"的中间态挪了面板。**
> ✅ **2026-09-16 晚已修好并真机验证**，完整数据/探针配方见 `DEVLOG-面板跳动-2026-09-16.md` 第 7 节。
>
> 现象：面板开着时关掉「网速」（图标减少、面板右移），箭头**先向左跳一下、再跳到右边**；
> 开「网速」（图标增加）则正常。
>
> 逐毫秒探针量到的因果链（一次换档，窗口 229 → 184）：
> ```
> t=7.0007  脚本：关「网速」
> t=7.0189  系统挪面板 → 903   status=(x=995, w=184)  ← 用「旧 x 995 + 新宽度/2 92」当中心
> t=7.0215  状态栏窗口 RESIZE 到 184（x 仍停在 995）
> t=7.0244  面板 → 948（正确位置）                     ← 我们的预测在同一轮 runloop 内纠正
> t=7.0449  状态栏窗口 MOVE 到 x=1040（真正的中心 1132）
> ```
> 两条关键事实（都是直接量到的）：
> 1. **系统改宽度时会当场把面板按「旧 x + 新宽度」重摆一次**，而窗口的 x 要 15~30ms 后才就位，
>    那一下**差 45pt** —— 这就是用户看到的"反向跳"；
> 2. **变宽方向系统根本不挪面板**（实测窗口 184→229、x 1040→995，面板全程没动）——
>    所以"只有一边跳"不是错觉：那个方向只有箭头滞后，没有跳。
>
> 修法（`StatusItemController`）：
> - **新增 `reanchorForPredictedResize()`**：在 `updateStatusItem` 里设完 `button.image` 之后
>   **立刻**用「右边缘守恒」预测最终窗口位置（实测右边缘恒为 1224，两个方向、四次切换全成立）：
>   `最终 x = 上次定位用的右边缘 − 新宽度`，把锚点摆到**预测中心**上当场 `show` 一次。
>   ⚠️ 参考值必须用 `lastStatusWindowFrame`（上一次**真正用于定位**的 frame），
>   **不能现读 `button.window.frame`**——那一刻它正是中间态，现读就等于复刻系统的错误。
> - **`syncPanelAnchor()` 保留**：判据只看 **x** 变化（x 的最后一次变化才代表排版完成），
>   负责"最终一定精确"，以及"别的 App 图标增减导致窗口移动"这类我们没预测的场景。
>   两条路径的**顺序不能反**：先预测、后 sync，否则会被 sync 的中间态判据覆盖。
> - 特意**没有**再引入去抖 / 定时器校正 / 收面板重开。
>
> 验证（同一个 2×2 矩阵；判据是"错误位置有没有被 3ms 采样在 **runloop 边界**观测到"，
> 后者才等于"有没有真被画出来"）：
>
> | | 错误位置累计 | 被画出来 |
> | --- | --- | --- |
> | 修复前（判据只看 x） | 218.5 ms | **8 次**（903 差 45pt，每次约 20ms） |
> | 修复后 | 12.1 ms（每次 5~6ms，全在同一轮 runloop 内） | **0 次** |
>
> 预测命中率 4/4（预测 1040 / 995 / 1040 / 995 = 系统最终值）。
>
> ⚠️ **残留**：锚点矩形必须落在按钮范围内，否则系统会**静默忽略**这次 `show`。
> 所以当换档把宽度缩到**不足原来的 2/3** 时预测无法表达 —— 现实中只有"面板开着时排版档位变了"
> 够得着（单行→极简：预测中心落在 localX=185、按钮只有 88 宽），此时回落到 `syncPanelAnchor`，
> 错误位置约 43ms（**与改动前一致，不是回归**）。切显示项一次只少一段（约 20%），够不着这个条件。
> 彻底解决要自己造 1pt 锚点视图挂到按钮上（让坐标空间由我们控制），本次没做，理由见 DEVLOG 7.6。
>
> ⚠️ **走过的弯路（别再走）**：去抖 60/120ms、只等 x 变化、16ms 定时器持续校正、
> "收面板稳定后重开"（用户明确否决）、"alpha=0 隐藏再定位"（`show` 在 alpha=0 时连调用都不返回）。
> 共同错误是都在回答"**我该什么时候喊 `show`**"，没问"**为什么系统要摆那一下**"。
>
> ⚠️ **`popover.show` 的另一个坑**：面板已显示时，若目标位置与当前位置**完全一致**，这次调用会被系统吞掉
> （实测 `before=902 after=902`）；目标不同则生效（实测 903 → 948 成功）。
> 所以纠正要靠"**算出一个不同的正确位置**"，而不是"多喊几次 `show`"。
>
> **教训：`NSStatusItem` 的窗口在换档时会分多拍、异步地变化，任何"跟着它定位"的逻辑都必须能容忍中间态。**
> 现在这套的分工是：**预测负责"别让错的那一帧被画出来"，`syncPanelAnchor` 负责"最终一定精确"**。

> **bug 6（2026-09-16 晚，"自动适应换档太慢"）：降档窗口 5 拍 + 升档用了偏小的宽度。**
> 现象：菜单栏里图标一多，该从单行变双行，但要等好几秒（体感"半天不动"）。
> 完整排查、探针配方与对照数据见 `DEVLOG-换档适应延迟-2026-09-16.md`。
>
> 实测两个原因叠加：
> 1. **降档判据和升档共用一个"最近 5 拍取最大值"的窗口** → 真的变挤要等 5 个采样被挤出去
>    （刷新 2 秒时 **8~10 秒**）。窗口长是为了抗"折叠区瞬时跳变"（实测单拍 440pt 级），
>    但用 5 拍换来的保护，2 拍其实也有（两拍取最大时尖峰被上一拍的旧值压住）；
> 2. **升档用的宽度是启动那一刻量到的 159pt**（真实 213pt）：数据没到位时 GPU 段整段缺失，
>    量出来的宽度偏小；升档判据 `eff − gain ≥ 安全区+40+buffer` 里 gain 算小了一半，
>    于是把一个**放不下**的单行档升了上去（窗口落到 954pt，进折叠区完全不绘制），
>    同样是 5 拍之后才退回来。实测那 10 秒里图标在屏幕上**完全没有**（`build/shot-A-加图标前.png`）。
>
> 修法（`StatusItemController`）：
> 1. **降档改用 2 拍窗口**（`downgradeWindowSamples`）：`max(最近 2 拍 minX) − (安全区+40)`。
>    升档**仍然用 5 拍**——升上去放不下会被刘海整条吞掉，那一头宁可保守；
> 2. **三档宽度用完整快照预先量准**（`primeDensityWidths`）：`gpuUsage == nil` 时渲出的宽度不记账，
>    并在第一份完整快照到达、以及显示项组合变化时，把三个档位各渲染一次只取尺寸。
>    （顺带把 README bug 3"没渲染过的档位宽度是 0"的根源也解决了。）
>
> 对照实测（同一份构建，同一个触发——把我们的项往左挤 60pt）：
>
> | 降档窗口 | 挤走 → 决策 | 挤走 → 真的画出来 |
> | --- | --- | --- |
> | 5 拍（改动前） | 8.02 s | 8.08 s |
> | **2 拍（改动后）** | **2.02 s** | 2.08 s |
>
> ⚠️ **顺带否掉一条猜测**：实测往菜单栏加 5 个 34pt 的图标，我们的项 `minX` **全程不动**
> （系统把新图标塞进 `«` 折叠区），所以"加图标"本身不一定挤到我们；真正让项移动的是
> **它自己的宽度变化**（升档）或系统整体重排。无论哪条路径，"变挤 → 换档"这段延迟是同一个。
> 另外刷新周期只决定一拍多长：把「刷新」从 2 秒改成 1 秒，所有延迟直接减半。

如果连极简档都显示不出来，说明右侧真的没位置了，可以：

1. 退出几个占用菜单栏的 App（按住 ⌘ 拖动图标可以移除系统图标）；
2. 面板 →「显示项」里关掉部分指标，图标会进一步变窄；
3. 改用「自动适应」，让它自己缩到能放下为止。

> 极简档为了省宽度只保留下行速度，上行速度、CPU/内存/GPU 的完整数值在
> 鼠标悬停提示和下拉面板里都有。

## 开发备注

- **面板箭头跟着图标宽度走（2026-09-16 已修复；含"换档反向跳"）**
  两个场景都要覆盖：**① 面板开着时切换显示项**；**② App 刚启动时"两行档自动升成单行档"**。
  1. `NSPopover` **不会跟着锚点自己走**——面板开着时图标宽度变了，面板停在原地，
     实测甚至会**反向跑**（图标中心左移 54pt、面板右移 54pt，偏差变成 +107.5pt，
     箭头直接指到图标边缘）。必须自己补一次 `show`。
  2. **触发条件要用"状态栏窗口动了"，不要用定时/延时猜测**。窗口 frame 的变化是
     "系统开始挪它"的最直接证据。之前试过"等一个 runloop"（太早，读到旧位置）和
     "延时 50ms / 循环追 50ms×12"（在**启动升档**场景会错过——那次换档要等下一次数据刷新，
     几百毫秒后才发生）。现在这套检查每次重绘都会跑（**含流光的 15fps 帧**），
     没变化时只是一次数值比较，开销可忽略。判据分两处，**都不是"整个 frame 变了"**：
     ```swift
     // ① 宽度变了（在 updateStatusItem 里、设完 button.image 之后同一轮）→ 按预测定位一次
     reanchorForPredictedResize(previousImageWidth: …, newImageWidth: image?.size.width, button: button)
     // ② x 变了（每次重绘都查）→ 排版完成，精确纠正一次
     let xMoved = (lastSeenStatusWindowX != nil && lastSeenStatusWindowX != win.frame.minX)
     lastSeenStatusWindowX = win.frame.minX            // 观测记账
     guard isPanelOpen, xMoved else { return }
     showPanel(at: button.window?.frame ?? win.frame, button: button)   // 定位前重读 frame
     ```
     为什么"某一维变了"不能当"排版完成"：宽度先变、x 后变，见下一条。
  3. ⚠️ **系统换档时"分两拍"改状态栏窗口，中间态绝不能被用来定位**（详见上文 bug 5）：
     先改**宽度**（`x` 不动），15~30ms 后才改 `x`。而系统**在改宽度那一刻就会把面板
     按「旧 x + 新宽度」重摆一次**（实测差 45pt，就是那下反向跳）。现在的处理是两段式：
     - **宽度一变就立刻预测**（`reanchorForPredictedResize`，在设完 `button.image` 之后同一轮里跑）：
       用**上次定位用的右边缘**减**新宽度**算出最终 x，把锚点摆到预测中心上 `show` 一次。
       参考值不能用 `button.window.frame`（那一刻它是中间态）；
     - **x 就位后再精确纠正一次**（`syncPanelAnchor`，判据只看 x 变化，定位前重读 frame）——
       它同时兜住"别的 App 图标增减把窗口挪了"这类没有预测的场景。
     - 顺序**先预测、后 sync**，反了会被 sync 的中间态判据覆盖。
     - 锚点矩形必须落在按钮范围内，否则系统的 `show` **静默失效**（残留见上文 bug 5 ⚠️）。
  4. **判据用自己维护的 `isPanelOpen`，不要用 `popover.isShown`**：后者在开合动画期间会滞后，
     实测会把对齐整段跳过。为此白查了很久。
  5. ⚠️ **调试这个 bug 时踩过的最大的坑：测量方法在骗人。**
     诊断脚本从 `popover.contentViewController?.view.window?.frame` 读面板位置，
     但**面板关闭后那个窗口对象还在**，于是读到的是陈旧坐标——一直报"偏差 +107.5"，
     让人以为修好/没修好，其实**面板当时根本没开着**。
     **教训：任何"面板位置"的采样都必须先确认 `isPanelOpen` 为真**，
     或者用 `CGWindowListCopyWindowInfo` 判断窗口**当前是否真的在屏幕上**。
     另外：**用截图从菜单栏反推图标中心也很容易被骗**——面板的标题栏、流光背景的亮边
     都会在菜单栏下方形成亮像素簇，被误当成图标。可靠的做法是"按列统计内容像素数再聚类"，
     并且把菜单栏和面板顶部**截进同一张图**再对比。
  6. **面板位移不做动画（2026-09-16 决定）**：`popover.show` 到新锚点是**一帧到位**。
     曾经用 `CVDisplayLink` 逐帧插值锚点做过平滑滑动（60fps 已调通），但**已按需求回滚**，原因：
     - 换档时**系统会抢先把面板挪到新位置**（实测从 993 跳到 895），动画只能在它挪完之后
       从那一点开始滑——用户看到的仍是"先跳一下、再滑过去"，达不到"一路平滑"；
     - 试过用"面板真实位置"当动画起点去接上，但系统挪动与动画几乎同时发生，抓不到跳之前那一刻。
     **结论：`NSPopover` 把面板位置和箭头位置绑成一体、且系统会自己挪它，
     在这套 API 上做不到"一路平滑滑动"。** 真要平滑只能放弃 `NSPopover` 自绘面板
     （位置和箭头都自己逐帧动画，代价是开合、外部点击收起、键盘焦点都要自己做）。
     另外两个记录在案的结论，避免后人重走：
     - 用 `NSTimer` 驱动动画会掉帧（挂主 runloop，被 15fps 的流光挤后，0.22 秒只出 5 个中间帧）；
       `CVDisplayLink` 能稳定 60fps。
     - **不要用 `win.animator().setFrame(...)` 动画窗口**：面板虽平滑，但箭头不会跟
       （箭头由系统按锚点绘制），且动画结束再 `show` 会把窗口弹回锚点（实测跳 200pt）。
  7. **验证结果**：
     - **换档跳动（2026-09-16 晚，逐毫秒探针）**：同一 2×2 矩阵下，"面板停在错误位置"的累计时长
       从 **218.5ms 降到 12.1ms**，且**被 3ms 采样在 runloop 边界观测到的次数从 8 次降到 0 次**
       （= 那一帧从来没被提交到屏幕）。预测 4/4 精确命中系统最终 x。数据见 DEVLOG 第 7 节。
     - 换档对齐（2026-09-16）：真实单次切换场景面板 `947 → 924` **一次到位**；
       面板窗口中心 **1108** = 图标窗口中心 **1108**。

     | 场景 | 图标窗口中心 | 面板箭头 | 偏差 |

     | 启动升档前（两行） | 1162.5 | 1162.0 | −0.5 |
     | 启动升档后（单行） | 1108.5 | 1108.0 | −0.5 |
     | 面板开着切显示项（三项） | 1131.0 | 1131.0 | +0.0 |

     偏右约 21pt（系统渲染图片时的位置特性，与代码无关）。要对齐到"可见内容中心"
     需要再做一次纯色图标标定。
  9. **踩过的错误量法（别重走）**：
     - `bounds.midX − (iconWidth − 105.5)`：`105.5` 来自"分两次识别面板深色区域与菜单栏
       白字再各算中心"的错误方法，中途混进了别的深色窗口；实测随宽度恶化到偏 121pt。
     - 「箭头尖端恒比锚点中心偏左 14pt」：某轮量到的结论，换配置复测又变成偏右 17pt，
       说明该常数与状态项在菜单栏里的位置/宽度有关，**不能当全局常量照抄**。
     - 菜单栏右侧图标密集，**别用"亮像素范围"推断图标中心**——相邻的 VPN／天气／输入法
       图标会被算进来（本次因此量出过 1216、1340、1379.5 等越界值）。
       可靠的隔离方法是"按列统计内容像素数再聚类"，SysPulse 会成为独立的一簇。
     - `screencapture` 的 `-R`/`-l` 单位是**点**、输出是 **2 倍像素**；
       `CGWindowList` 的 `bounds` 原点在**左上**、`NSWindow.frame` 在**左下**，别混用。
     - **别用"裁剪菜单栏再找亮像素簇"来定位图标**（2026-09-16 又踩一次）：面板的标题栏、
       流光背景的亮边都会落在菜单栏下方，被当成图标簇——据此量出的"图标中心"能偏 70pt。
       要么把**菜单栏和面板顶部截进同一张图**再目视 + 量色带边界，
       要么让 App 自己 3ms 采样 `popover` 窗口的 frame（见 HANDOFF 第 7 节配方）。
     - **用 `CGWindowList` 读不到菜单栏图标窗口**：`Tools/winlist` 只能列到面板窗口
       （`layer=25`，`368×533`），状态栏项本身的窗口不在列表里——想拿它的 frame
       只能在 App 内读 `statusItem.button?.window?.frame`。
- **`defaults write` 改不了正在运行的 App 的显示项**：`Preferences` 是内存缓存的
  `ObservableObject`，不监听外部改 plist。想用脚本复现"切换显示项"，要么在 App 内点，
  要么**先改 plist 再启动**（启动时才会读到）。2026-09-16 复核：即使 `pkill -x cfprefsd`、
  确认 plist 已是新值，重启后 App 仍可能读到旧值——不要在这条路上耗时，用 App 内钩子。
- **`codesign` 会改变文件内容，别拿未签名产物和已安装产物比 md5**：`build/SysPulse`
  未签名是 931600 字节，`codesign --sign -` 之后变成 945376 字节、内容不同。
  这次为此误判成"装的还是旧版本"，白查了几轮。要判断版本是否更新，应该比
  **时间戳**，或者在签名后再比。
- **面板里第一次点击失效**：状态栏 App 平时不是活动 App。如果不先激活 App 就
  `popover.show`，面板里控件的第一次点击会被系统用去「激活 App + 让弹窗成为
  key window」，这次点击不会传给控件——表现就是点「刷新／显示项／启动」没反应、
  面板闪一下，要点第二次。修法是在 `show` 之前调用
  `NSApp.activate(ignoringOtherApps: true)`。
- **连续点击开不了关，是三个坑叠在一起**（都能让 `isShown` 与实际状态不一致）：
  1. **不能用 `popover.behavior = .transient`**：点状态栏图标时系统先把弹窗当成
     「点了外部」自动关掉，紧接着按钮事件才到达，此时 `isShown` 已是 `false`，
     于是又把它重新打开——怎么点都关不上。改用 `.applicationDefined`，自己管外部点击。
  2. **全局鼠标监听必须排除状态栏图标自身的区域**：状态栏项的窗口属于 WindowServer，
     对全局监听来说也算「别的 App」，不排除的话每次点击都会先被监听关掉、
     再被按钮 action 重新打开，表现就是「快速连点被吞」。
  3. **不要用 `popover.isShown` 判断开关，动画期间会滞后**：开合动画期间它一直是旧值，
     快速点击会被误判成反向操作。改为自己维护 `isPanelOpen`。
     另外 `NSApplication.didResignActiveNotification` 不能用来收起面板——
     附属 App 被激活约 470ms 后系统会把激活状态收回，导致面板刚打开就被自己关掉。
  4. **动画进行中系统会忽略反向操作**（实测窗口约 520ms）。所以动画期间收到的点击先
     记为 `pendingToggle`，等 `popoverDidShow` / `popoverDidClose` 到达时再补做一次，
     点击就不会丢。实测 40ms～600ms 各种间隔连点都能准确开关。

> 代价与取舍：`NSPopover` 的动画时长由系统固定（本机实测展开 629ms，其中动画占 519ms；
> 关掉动画后只要 112ms），公开 API 只能选「有动画 / 无动画」，不能调速。
> 想做到"快而不生硬"（比如 120ms）只能不用 `NSPopover`，自己画面板 + 自己做动画。
>
> **当前选择：关掉动画**（`popover.animates = false`）。系统动画由 WindowServer 绘制，
> 帧率观感发卡，而且时长不可调；关掉后展开约 110ms，明显跟手。
> 想换回动画只需把这一行改成 `true`，连点已经通过 `pendingToggle` 记账处理，不会丢点击。
- 本机命令行工具链缺少 `SwiftUIMacros` 插件，因此源码中不使用 `@State` 等 SwiftUI 宏，
  改用 `ObservableObject` + `@Published`。（完整的 Xcode 环境不受此限制。）
- `swift build`（SwiftPM）在沙盒环境下会因 `sandbox-exec` 受限而失败，`build.sh` 因此直接
  调用 `swiftc`；在普通终端里 `Package.swift` 仍可正常使用。
- **改偏好不要顺手重启采样定时器**：最早「任何偏好变化都重启定时器」，于是切换一个显示项
  会在极短时间内把状态栏重画两次（立刻一次 + 刚重启的定时器紧接着又一次），观感上像闪了两下。
  现在只有 `refreshInterval` 变化才重启定时器，其余偏好只触发一次重画。
- **开销实测（2026-09-16，`Tools/CPUSpy`，每档 8 秒均值，M5）**：
  | 状态 | CPU | 常驻内存 |
  | --- | --- | --- |
  | 流光关闭 · 面板关闭 | **0.02%** | 47 MB（冷启动）/ 86 MB（面板开过一次后） |
  | 流光开启 · 面板关闭 | **0.13%** | 50 MB |
  | 流光关闭 · 面板打开 | 0.07% | 86 MB |
  | 流光开启 · 面板打开 | 0.19% | 96 MB |
  几点说明：
  - **流光大约多花 0.11% CPU**（0.02 → 0.13）。绝对数不大，但它是**持续重画**
    （15fps），对续航的影响比这个百分比看起来大，所以默认关闭、关掉时定时器立刻销毁。
  - **面板打开会多花约 0.05% CPU**：`NSHostingController` + 整个 SwiftUI 视图树
    跟着数据每秒重绘（关闭时释放视图能回到基线）。
  - **内存的两个数字不要混淆**：47MB 是"从没开过面板"的冷启动值；开过一次面板后
    弹窗窗口约 38MB 由 AppKit 持有、**连换掉 `NSPopover` 对象都回收不了**，
    所以之后会稳定在 86MB 左右。这是系统行为，不是泄漏。
  - 测量方法：`./build/CPUSpy <pid> <秒数>`，用 `proc_pidinfo` 读 CPU 时间差与常驻内存。
- **底部菜单选完要顺手收起整个面板**：底部「刷新 / 排版 / 启动」三个菜单里选任一项之后，
  面板会一起收起（`DashboardView.onMenuSelection` → `StatusItemController.closePopoverIfShown()`）。
  理由：这些都是一次性设置，选完面板留在屏幕上只会挡视线。
  两个坑：
  1. `NSMenu` 自己会关闭，但面板是独立的 `NSPopover`，**不会跟着关**，得自己收。
  2. **别在菜单项 action 里直接 `performClose`**：那时 `NSMenu` 还在收尾，
     实测 `popover.isShown` 会立刻变 `false`、窗口却仍然留在屏幕上。丢到下一个 runloop
     （`DispatchQueue.main.async`）再关才干净。
  另外：**验证"面板是否真的关掉"不要数 `CGWindowList` 里的窗口数**——关掉之后那个窗口
  还会在列表里待着（陈旧窗口）；要么截图看像素，要么比对面板区域的图像哈希。
- **指标开关为什么不在菜单里**：原本「显示项」菜单里放着四个指标开关，但 macOS 上
  SwiftUI 的菜单项**点一次一定会收起菜单**（`menuActionDismissBehavior(.disabled)` 在 SDK 里
  被标成 `@available(macOS, unavailable)`，只有 iOS 能用），没法连续勾选。
  于是把开关挪到面板上做成小开关，菜单只留「排版」这类单选项。
- **菜单栏「流光」背景（`preferences.menuBarGlow`，默认关闭）**：整条状态栏项的背景铺一层
  **横向流动的彩色渐变**，文字画在最上层。**没有"流光 API"这种东西**，是公开积木拼的：
  1. 图标本来就自绘成 `NSImage`（`MenuBarImage.render`），所以"背景"就是在写文字之前
     先画一个渐变圆角矩形（`MenuBarImage.drawGlow`）；
  2. 颜色在 `NSColor(hue:saturation:brightness:)` 里按时间推色相，等价于 SwiftUI 的
     `.hueRotation`——**它在部署目标 macOS 14 上就可用**（`MeshGradient` 要 15、
     `.glassEffect` 要 26，本项目用不了）；
  3. **三组色带、相位各差 120°**，每组用一个正弦"包"控制明暗（正弦一明一暗就是一道色带）。
     三组错开才表现为"整条上此起彼伏的彩色流动"，而不是一道光从左扫到右。
  4. 只做**横向**渐变（`angle: 0`）：竖向恒定，否则那一丁点高度会从紫到蓝糊掉。
  5. 一个 15fps 定时器推进相位，**每帧只重画这一层渐变**；文字的排版与绘制仍然只在数据
     刷新时做一次，所以开销可控。
- **流光的观感参数**（都在 `MenuBarImage.drawGlow` / `StatusItemController.startGlowTimer`）：
  | 参数 | 当前值 | 作用 |
  | --- | --- | --- |
  | `baseHues` | `[0.58, 0.75, 0.50]` | 蓝 / 紫 / 青三组色相 |
  | `saturation` / `brightness` | `1.08` / `1.25` | **颜色亮不亮**（见下） |
  | `alpha` 系数 | `0.46` | **整体浓淡**：越小越透（0.24 极透、0.44 偏实） |
  | `cycle` | `240` pt | 色带波长，越小色带越密 |
  | `turns` | `2.5` | 横向流动速度 |
  | 定时器 `12.0` | 12 秒 | 走完一相位周期的时间 |
  **"更亮"和"更浓"要分开调**（只调一个达不到效果）：
  - **更亮** → 调 `saturation` / `brightness`（brightness 可以超过 1，因为各分量相加后
    本来就会 clamp 到 1；提亮会让色相看起来偏青，是正常的加法行为）；
  - **更浓** → 调 `alpha` 系数。
  只提亮会显得淡、只加 alpha 会显得暗，两者要一起给。alpha 的演变：
  `0.62` → `0.42` → `0.32` → `0.24` → `0.34` → `0.40` → **`0.46`（当前，配 brightness 1.25）**。
  中途试过在光带之上"手搓"玻璃质感（顶部高光 + 亮边 + 底缘暗边），**已按需求去掉**。
